# T-008 Qwen3-8B 基础 SFT 完整方案

版本：review-v0.1。日期：2026-10-19（America/Los_Angeles）。状态：待负责人审阅讨论，非执行冻结版。

本方案把 Data-Juicer、EvalScope、ClearML 接入自我认知与通用指令基础 SFT 的完整流程。训练起点已经确定为原始 Qwen/Qwen3-8B＋新 LoRA；三个工具采用最小接入范围，按阶段运行并用版本清单关联结果。本文中的数据选择、参数、题量、评分阈值和执行安排均为待讨论建议，不能据此启动作业。

本轮交付仅为方案、版本记录和文档回读。不清洗或改写语料，不生成训练衍生集，不改训练代码，不创建 ClearML 实验，不运行评测或训练，不改变集群服务。

## 4. 工具职责与最小接入范围

Data-Juicer：读取受控工作副本及分析投影，统计分布、标记疑似异常和重复；按确认的规则执行处理，输出报告和候选结果。它不自动决定语义正确性、数据使用权或训练准入。

EvalScope：统一组织正式题集和公共基准运行，调用指定模型、执行评分插件、输出分项及对比报告。项目特有的身份规则、thinking/正文诊断、哈希核验作为薄适配层接入，避免另建独立评测平台。

GitHub：保存本方案、工具配置、适配代码、审核记录索引、运行与对象清单；以 commit 和文件 SHA 定位。模型大文件保持内容寻址及明确的备份位置，不反复进入 Git。

K8s：承载有明确资源和退出条件的阶段 Job、PVC 及服务。现有脚本负责少量身份绑定、数据与产物核验和结果转换。

本轮不建设自动调度 DAG、ClearML Agent 队列、自动调参、自动择优 checkpoint 或自动发布。Langfuse 和 Label Studio 不成为实施前置条件；如后续确需审核界面，再单独确定接入范围。每阶段一个可复现入口和结果回执即可，操作者不应重复填写同一版本信息。

## 5. 数据选择与处理方案

### 5.1 父快照和配比建议

建议以历史 native-loaded 2600 次曝光的完整快照为审核父对象，便于与实际首轮输入比较；其字节 SHA-256 为 d85dbe58d9c5fab98bbf6a81cf828147ba1a47d6cce492aef107c7d3dafa604c。该选择待负责人确认，不从过滤后 1642 行反推审核完整性。

保留 original-v1.2 2600 行快照（SHA-256：dda551041a12c460b84056f2c58df0ab60f2e9999e0518f116cf5f5b3c5faf6e）作为来源与差异依据。两者行号、顺序、内容摘要不能混用；选择另一个父对象时要重新绑定全部处理决定。

来源仍为 swift/Qwen3-SFT-Mixin 与 swift/self-cognition:qwen3。建议本轮不重新下载、重采样或机械补足条数；先复用现有快照，保留未被处理的曝光分布。#2000/#600 是曝光配置，不代表独立记录数；身份 600 次曝光包含 108 种记录。清洗后真实条数和配比由报告给出，不能提前写成仍为 1642 或指定比例。

### 5.2 Data-Juicer 分析及异常审核

对父对象创建受控分析投影，每条绑定父快照 SHA、原始零基行号、原始行字节摘要和内容摘要。Data-Juicer 的展示文本仅用于分析；不能将拼接文本反向替代原 messages、角色或轮次。

最小分析范围：JSON/messages 结构、角色与顺序、空内容、身份占位符、异常字符、完全重复和曝光分布、疑似近重复、答案完整性及思考标签异常。语义问题可先标记，最终由审核决定；来源和许可证据随版本保留。

重复统计不能直接驱动删除。身份模板的重复可能是采样权重；先按不同记录审核，必要时标记出现位置特有的问题，再映射到全部曝光。开发集与评测集的防泄漏按内容/模板族和实际来源检查，不能把重复曝光随机切开当独立验证。

异常清单记录类别、证据、建议、决定者、实际时间、处理方式及决定引用。处理类别为：保留、排除、待核查；需要改写时单独提出正文变更版本和逐条差异，不能借清洗自动润色、补答案或伪造审核结论。

历史 958 次超2048、302种/604次未闭合think等统计作为问题线索，不能直接变成本轮批量删除名单。尤其不能把删除 think 标签等同于修复推理或回答完整性。

### 5.3 冻结可训练输入

拟继续采用2048训练长度，但要经分布报告和讨论确认。超过长度先列清单并评估处理代价；不自动截断、不静默 delete，不为了保条数自行增大长度。如必要内容大量超长，回到方案讨论决定长度或数据变更。

经确认的排除操作由可追溯衍生步骤执行，未排除记录的原始字节和顺序保留。Data-Juicer 输出候选与该结果逐条比对；通用 JSON 序列化不能悄悄改变冻结输入。已有 derive_snapshot.py 限定 old_original 2600 格式，须适配父快照合同后才能处理 native-loaded，不能直接套用旧脚本。

输出 train.jsonl、父子 manifest、异常清单、处理决定、排除清单、重复分布、实际独立记录数和曝光数。若有改写，另存前后映射和新审核记录。

随后在固定环境用真实 Qwen3 Tokenizer 无截断编码，并通过实际 ms-swift 模板和数据入口检查：总行数、顺序/成员、有效监督 token、loss mask、思考结构、零超长、零静默丢行。通用长度统计不能替代该检查。训练必须读取核准的本地 train.jsonl；准入失败先停止，不以默认过滤补救。

独立题由未参与训练调优的隔离评测角色准备或受控接收，冻结后不向训练者展开题文和逐题失败。训练前正式原版/旧候选结果由评测侧留存；只回报约定汇总及阻断项，不将独立题反复用于选配方。新候选冻结后执行对应条件，设置完全一致时复用基线；若中途配置漂移，应明确宣布不可比并重新安排，不能拼接分数。

本会话换角色不算独立审核；后续如使用子代理，须按真实隔离输入建立，不继承训练讨论和已曝光测试答案。当前没有创建评测角色或测试题。

## 8. EvalScope 正式评测设计

### 8.1 对照条件与输出记录

原版两组为A（无定制System）和B（有定制System）；旧Adapter为C旧/D旧；新Adapter为C新/D新。B、D旧、D新的定制System逐字节一致；无定制身份组仍使用相同必要协议上下文，不暗藏身份提示。

thinking与nonthinking分开运行和报告。每组记录模型/Adapter SHA、引擎及版本、模板、System SHA、题集SHA、生成设置、错误状态和原始输出定位。相同条件固定seed；固定seed不保证跨引擎或硬件完全复现。

建议沿用现有脚本的候选生成设置：seed42；thinking temperature0.6/top_p0.95/top_k20/max_new_tokens4096；nonthinking temperature0.7/top_p0.8/top_k20/max_new_tokens1024；min_p0.0。实际工具若不支持某字段，必须显式评估差异，不能忽略。提示词长度＋生成预算不得越过经核验的实际推理上限；2048训练长度不等于推理窗口。

每条保存是否正常结束、是否截断、正文是否存在、思考标签状态、耗时、输出token及错误原因。HTTP200、正文非空和训练loss均不能直接算回答正确。多轮按整段对话通过判分，同时保留逐轮诊断；提前中断算失败，不能缩小分母。

### 8.2 题量建议与预算

独立专项建议120个案例：身份40、通用指令/理解/算术/代码/中英文/多轮40、缺信息澄清20、能力与基本安全边界20。题量、语言覆盖和多轮轮数须事前冻结，独立案例不复制训练模板。

另建议公共基准60题：可验证指令遵循30、基础数学30，作为补充回归，不宣称公开题是未曝光独立测试。候选来源为EvalScope支持的IFEval、GSM8K；最终选用其当前版本实际支持的数据集和合法可用固定成员，记录许可、配置及成员SHA，不只写随机seed或limit。中文和代码覆盖由专项题补足。

专项120×6个条件×2模式＝1440个案例条件；公共基准建议在无定制System的原版/旧/新三模型上运行，两模式共60×3×2＝360个案例条件，总计1800。多轮增加实际生成次数；失败重试不自动计成新样本。正式重复次数默认1，波动复核需单独预登记，不默认重复全套。

正式计分前用微型样例实测吞吐和平均输出长度，形成总GPU时间及输出token预算。1440专项单轮按上述上限最多约368.6万输出token，不能把它当实际耗时承诺。若成本超窗口，应在正式看分前共同缩减题量/条件并更新协议；不能看结果后删难题。

### 8.3 评分与讨论阈值

格式、算术和明确约束采用确定性评分。身份、真实性、澄清与边界采用冻结rubric独立审核；可选LLM辅助评分须先验证与人工标注的一致性，并另行明确模型、费用及数据流，本轮不默认调用外部裁判API。

以下为待讨论的内部判据，不是监管标准：

- C新身份每种模式至少38/40（95%），D新同样报告；定制主体与基础模型来源混淆、严重虚构权限/能力须逐项处理，不允许被总体分数抵消。
- A对C新、B对D新的通用能力差值逐项报告；下降超过3个百分点触发复核并暂不自动通过。40题中一题即2.5个百分点，小样本不能证明统计意义上的“无遗忘”；同时提供计数、分母和不确定性说明。
- 正常可回答专项题须有完整可见答案；空正文、截断或协议错误不算成功。冻结阻断用例不得有未关闭问题；模型层与UI层分别记录，不用离线通过关闭暂缓的WebUI故障。
- 澄清及基本边界建议各至少18/20，严重能力失实和关键安全错误为阻断项；具体严重错误定义由协议固定。
- 旧/新候选并列比较，最终验收不只看是否超过旧候选，也必须满足相对原版和身份目标。

EvalScope输出机器可读结果及可读报告。独立Reviewer提供真实引用、评分汇总和分歧处理；ClearML登记评测Task并关联受测Model。逐题原文和回答受控保存，只上传允许的汇总及摘要索引。评分不明确的项目先进入复核，不能默认通过。

## 9. 拟定训练配方和停止条件

建议优先保留历史可运行的BF16 LoRA路线：r8、alpha32、all-linear、dropout0.05；1 epoch；learning_rate 1e-4；单卡batch1、gradient_accumulation16；warmup_ratio0.05；seed/data_seed42；gradient checkpointing启用；workers4。无QLoRA、Liger或多参数网格搜索。

训练长度建议2048，最终以第5节处理和讨论结论为准。有效监督样本数、曝光数及最终步数由冻结输入和实际数据加载计算，不能硬编码103步。验证实际解析出的完整命令和参数，保留必要兼容性修复。

保存策略建议每50步及最后一步保留checkpoint，并保存真实终态信息和必要优化器状态。最终候选固定为本次完整1 epoch的最后checkpoint，不依据独立题成绩在多个checkpoint中挑选；磁盘容量在预检中确认，历史产物不清理。

GPU顺序建议为3步Smoke后一次Full；两者从同一原始基座各自新建LoRA，Full不继承Smoke权重。Smoke只验证数据、计算、记录和保存链，不能代替效果评测。未经讨论不追加训练轮次或改变参数反复择优。

出现数据/基座/代码/镜像哈希不一致、静默丢行、空监督、非有限loss、OOM、写盘失败、终态步数不一致时停止并保留首个失败证据。ClearML传输失败与训练计算失败分开记录：本地证据保留，候选交付保持待回读，不能为补上传重训或伪报成功。

## 10. ClearML 记录合同

用同一 experiment_group_id 关联实际数据准备、训练前对照、Smoke、Full和最终评测；各阶段各有独立 Task ID，创建只发生在真实执行时。训练模型使用独立OutputModel ID，旧Task和旧Model保持原样。

训练前绑定：方案冻结版本与SHA、Git commit、镜像digest和实装依赖、基座文件清单、父/子数据SHA、审核决定引用、模板/Tokenizer、配方及预检报告。

训练中复用进度桥接思路，至少记录optimizer_step、loss、learning_rate、epoch、耗时和终态；显存、grad_norm、token_acc仅在真实采集可用时记录，不补造缺失值。每个点绑定run和step，重启后去重；完整日志保存在本次受控输出目录。

训练后上传Adapter包与清单，强制下载核验字节SHA，再登记可交付候选。只登记Adapter不等于已备份整个16GB基座或完整优化器状态；完整checkpoint的PVC位置与备份范围单列。

评测中关联精确Model ID、题集及rubric摘要、推理配置、独立Reviewer引用和EvalScope报告摘要。评测Task完成表示评测流程结束；基础模型验收、PM签收和发布决定另有真实记录，不由代码自动生成。
