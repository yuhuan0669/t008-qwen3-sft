# T-008 Qwen3-8B 基础 SFT 方案

版本：review-v0.3。状态：待审阅。当前只更新方案和版本记录；数据处理、GPU作业和训练待后续确认。本文是完整的当前方案，修订说明与四份参考意见放在 docs/reviews/review-v0.3/，历史版本保留。

## 1. 目标与身份口径

以原始 Qwen/Qwen3-8B 新建 LoRA，训练稳定的产品身份，同时保持通用指令能力、完整回答、必要澄清和能力边界。旧 checkpoint-103 仅用于开发诊断。T-011 并行准备行业数据；第二阶段须节点A、B2通过并由PM批准。

中文名：章鱼能碳垂直大模型。英文名：Octacarbon LLM。研发／训练主体：能碳章鱼（湖北）人工智能科技有限公司 / Octacarbon (Hubei) Artificial Intelligence Technology Co., Ltd.。

日常“你是谁”回答产品身份；“谁开发／训练了你”回答公司即可，不要求主动提Qwen。明确询问底层开源模型或原始权重时，回答Qwen/Qwen3-8B。询问“你是Qwen吗”按语境区分产品名和基座来源。普通任务不强行插入身份，也不因产品名称带“垂直”就声称已验证专业碳核算或运维能力。

主要验收对象是无定制System的新候选C新；D新与原版加相同System的B比较副作用。

## 2. 数据：一份快照、一条处理流程

### 2.1 输入与处理

从现有 native-loaded 快照衍生：2600次曝光、1108种messages；身份600次／108种，通用2000次／1000种。快照和旧候选的精确定位沿用 registry/versions.json。历史保留1642条中未闭合think为0，空正文故障仍需按原任务另行诊断。

确定性脚本负责排除、有限身份修订和生成本地train.jsonl。Data-Juicer只出结构、长度、重复和异常分布报告；接口不适配时直接由脚本生成同样报告，记录使用的工具即可。

默认排除结构无效、真实思考块未闭合、应有最终回答却无正文、无有效监督、编码超过2048的记录。识别时区分结构标签和代码／引用中的字面标签，并抽查误判；不通过截断或补标签把坏样本变成合格样本。

逐条复核108种身份记录，按第1节修正名称缺失、明确基座问题失实、语病和无依据能力承诺；必要时补少量英文、多轮或来源问法。正常的“由能碳章鱼开发／训练”直接保留，不沿用旧口径的问题标签。每处改动记录原行、新内容和理由，审核结果随数据保存。

### 2.2 长度与配比

本轮固定2048，沿用已有可运行配置，去掉默认4096实验分支。报告被排除的类别及数量，用于后续判断数据缺口；本选择不以“4096必定无法运行”为前提。

清洗后报告身份／通用的曝光数、唯一记录数和assistant监督token占比。不凑2000／600旧总数，也不设置固定最佳比例。开发期可减少已审核身份记录的重复曝光，每种至少保留一次，保留成员和顺序由固定seed确定。新增通用来源或行业材料属于范围变化。

### 2.3 训练前检查

用真实Qwen3 Tokenizer、ms-swift qwen3模板和实际数据入口编码，确认成员与总数一致、零超长、零空监督、零静默丢行，并核对loss_scale=default+ignore_empty_think的实际展开及mask。训练读取通过检查的本地train.jsonl。

交付四项：训练文件、父子manifest、排除／修订清单、数据与编码报告。manifest记录父文件SHA、处理代码、规则和新文件SHA；改动清单用父快照行号定位，不再叠加每行多套摘要。未改写行保留原字节与顺序。

## 3. 工具与训练

### 3.1 工具分工

Data-Juicer负责辅助分析；脚本和ms-swift负责数据衍生与编码检查。EvalScope＋vLLM统一正式评测。现有Transformers＋PEFT脚本仅用于开发归因，发生具体差异时再用它核查。

ClearML沿用现有训练包装器登记Task与OutputModel。训练继续report_to=tensorboard，正常结束或异常退出后一次性解析指标并上传配置、日志及Adapter；上传后下载核验SHA。进度查看本地日志，不接实时桥接或原生Callback。上传故障保留待补传状态，不为补传重训。日志限定为训练指标与运行日志，评测题文及逐条回答留在评测目录。

每次Smoke／Full有自己的Task；正式评测用评测Task关联受测模型。数据报告作为附件，不另建准备阶段Task。已有版本清单和脚本自动生成的run manifest负责关联，减少人工填表。

### 3.2 初始配方与开发调整

初始配置：BF16 LoRA，r8、alpha32、all-linear、dropout0.05；1 epoch、learning_rate=1e-4、warmup_ratio=0.05；单卡batch1、累积16；max_length2048；qwen3模板、loss_scale=default+ignore_empty_think；seed／data_seed42、gradient checkpointing、workers4。

先跑3步Smoke，再做必要的Full，最多3次且受总GPU时间上限约束。每次从原始基座新建LoRA，用最后epoch的checkpoint作为该次候选。依据开发集选定最终候选，达到目标即停。

GPU包批准后，工程师可在学习率5e-5～1e-4、累积8或16、上述身份重复曝光调整范围内自主迭代；记录改动理由、数据SHA和结果即可，不逐次申请审批。实现修复和工具兼容修复也在包内处理。每次换数据重新编码检查；只有加载、计算、保存链发生变化时重做Smoke。

换基座、改长度、引入新数据来源、扩大实验次数或超出GPU预算时，再调整执行范围。数据／权重不符、静默丢行、空监督、非有限loss、OOM或保存失败时停止该次作业，保留日志后在包内排障。

## 4. 评测：开发快速诊断，最终一次验收

### 4.1 开发与留出

开发回归24题，用于身份双模式、通用和边界诊断；另保留40道公共开发题（IFEval20、GSM8K20），检查迭代中的明显退化。后者替代v0.2的100题开发集，与正式公共成员分离。

首次GPU工作先比较原版和旧候选的24题开发结果，检查权重、模板、输出预算和解析。旧候选尚未验收，保留诊断价值；不再进入大规模正式协议。后续每次Full只看开发结果。

正式留出为120题专项（身份40、通用40、澄清20、边界20）和200题公共基准（IFEval100、GSM8K100）。题集、rubric和阈值在训练前固定，由评测侧保管；训练侧不读取留出题及逐条失败。最终候选选定后，评测侧执行一次验收活动，含预定的重复seed。代码问题或能力问题区分记录。

### 4.2 后端预检

CPU上选少量代表性messages，核对训练模板与推理chat template的系统消息、特殊token、generation prompt和thinking前缀。比较对齐后的输入token；训练序列另含答案与loss mask，不要求完整训练序列等于推理prompt。

GPU上用4～8个非留出案例验证基座／LoRA选择、双模式、正文解析和结束原因，并测一次吞吐。确认加载的Adapter标识和参数，结合含混失败样例检查效果；不以某条答案不同作为唯一加载证明。取消常规24题双后端对比。

### 4.3 正式矩阵与成本

条件为A原版无System、B原版有定制System、C新、D新；B与D新的System相同。全部双模式。专项基线A／B单seed，新候选身份题3seed，其余单seed；公共只比较A和C新。

- 身份：40题×2基线×2模式＋40题×3seed×2新候选条件×2模式＝640。
- 其余专项：80题×4条件×2模式＝640。
- 公共：200题×2模型×2模式＝800。
- 合计2080个案例条件，其中基线880、新候选1200；分别较v0.2的4800和1600减少约57%和25%。开发及预检另外计入GPU预算。

生成设置沿用：thinking温度0.6／top_p0.95／top_k20／上限4096；nonthinking为0.7／0.8／20／上限1024；min_p0。默认seed42，身份重复用42／43／44。正文、终止原因、错误、耗时及token数由EvalScope统一记录。

基线设置不变时复用输出。正式看分前用开发吞吐估算剩余工作；如超过GPU包时间，先调整规模并固定新协议再生成正式成绩。双模式保留，不预设产品仅使用nonthinking。

### 4.4 评分与验收判据

格式、数学及可确定的短身份问答先自动评分。名称和公司命中是线索，评分需识别否定、引用和上下文；出现Qwen不自动算错。人工复核来源题、多轮／诱导题、自动未通过或不确定项，并随机抽查自动通过项10%（至少20条）。发现规则误判则修正规则并重评受影响结果。

澄清、边界按简短rubric人工评分。候选身份每种模式至少114/120次通过，并有38/40题至少通过2次；澄清与边界各至少18/20。预先列明的严重事实或能力虚构单列阻断。空正文、截断、协议错误计失败；多轮按整段对话评分。

通用按相同题目／seed比较A与C新、B与D新，公共按数据集及模式分别报告正确数、配对胜负和百分点差。B与D新的直接比较使用双方共有的seed42；新候选另外两个seed用于稳定性检查。下降超过3个百分点时，由评测侧复核新增失败的内容及影响，PM据此验收。报告注明样本数即可，不把复杂置信区间计算设为新增审批门槛。

另列无关身份插入和专业能力夸大次数。技术重试保留原因和首次结果；评分阶段复核已有输出，不追加采样挑最好成绩。最终未通过的候选保留失败报告；继续调优时另定独立验证安排。

## 5. 三阶段工作安排与共享GPU

阶段一：CPU准备。方案确认后，完成数据分析、身份审核与修订、编码检查、开发题及评测协议，形成候选数据和GPU工作量估算。阶段内常规工具适配、脚本修复直接推进。

阶段二：GPU包。负责人一次确认候选数据、配方及上述调整范围、最多3次Full、总GPU小时、窗口起止和恢复责任。包内连续执行开发诊断、后端与吞吐预检、正式基线、Smoke、必要的Full迭代和候选选择，无需逐步再批。诊断引出的包内身份修订按同一规则审核、重新编码后继续，数据SHA随run记录。

阶段三：独立评测与验收。候选冻结后评测侧运行1200个增量条件，合并基线并评分，由PM签收节点A。资源允许时，生成工作接在同一GPU窗口内完成；人工审核随后进行。三阶段不要求三个维护窗口。

历史资源为单张24GB RTX4090，与vLLM／UAT共享，执行前确认当前占用。每个实际窗口记录开始／截止时间、总时长与恢复负责人；进入前保存原服务配置和模型挂载，退出前恢复并检查健康。窗口预留恢复时间，新候选不自动替换服务；恢复失败立即报告。当前CPU工作及GPU包均未开始，具体窗口待定。
