先更正我上一轮的两处错误。第一，历史保留的 1642 行里未闭合 think 是 0，我当时推断它们进入了训练，这是错的。第二，“2000 余条独立记录”应为 1108 种。另外，v0.2 的膨胀有一部分是顺着我上轮 A4、A5、B1 的建议长出来的，下面也一并收回其中过头的部分。

结论是两种问题都有，而且都明显。技术判断大体合理，问题在于防御性文字和流程层级与任务规模不成比例。这是一次在单张共享 4090 上约百步的 LoRA 训练，方案却有 7 个授权阶段、4800 个评测条件、两套指标上报路线，外加一整节外部评审答辩。

## 一、过度防御（文字层面）

**角色混写。** 很多条款其实是给执行代理的行为约束，不是技术方案，例如“不得制造虚假 Model 或伪造 Reviewer”“未产生的 ID 保留 pending”“本会话换角色不算独立审核”。它们防的是代理虚报完成，对负责人读方案没有信息量，还在每一版里重复出现。如果这份方案是由代理起草和执行的，这类规则应放进工厂或项目层的常驻执行纪律，写一次，方案里引用即可。

**不改变任何行动的免责句。** 可以用一个检验标准来删：去掉这句话后，会有人做出不同的事吗？如果不会，就删。按这个标准，大量“不等于／不代表／不承诺／不宣称”都可以去掉，例如：
- “固定 seed 不保证跨硬件逐字复现”
- “官方资料证明功能存在，不证明集群版本兼容”
- “公开题不宣称从未被基座见过”
- “不能把 Adapter 上传说成完整灾备”
- “不承诺 24GB 必然足够”

第一节开头那串“本轮不改写、不生成、不修改……”属于本次交付回执，也不属于方案正文。

**重复和元内容。** 同一条规则在多节重复出现：不在 checkpoint 间择优（7、9 节），看分后不删难题（6、8.3 节），不擅自停 UAT（6、11 节），Reviewer 不能冒充（7、8.4 节）。第 2、15、16 节以及第 12 节末段基本都是变更记录和答辩，例如纠正外部评审的 540 应为 600，这对执行毫无影响。8.3 节“不采用临界补测”是在禁止一件没人打算做的事。这些内容应移到单独的 changelog。

## 二、过度设计（机制层面）

**评测规模已经超过训练本身。** 训练大约是一小时量级，评测协议是 4800 个条件，基线另有 3200。在共享卡上，评测才是停 UAT 的主要来源。建议做以下压缩：
- C旧、D旧 退出正式协议，旧候选已判定不合格，只在开发诊断里出现。
- 身份题的 3 个 seed 只用于 B、C新、D新。A 的身份必然回答 Qwen，跑 1 个 seed 作 sanity 即可。
- 公共基准只跑 A 和 C新。

这样算下来：身份 720＋80，其余专项 80×4×2＝640，公共 400×2×2＝1600，合计约 3040，比现在少近四成。如果再确定产品实际使用哪种 thinking 模式，非主模式只跑小样本，还能再减一大块，其中 GSM8K 在 thinking 4096 预算下最贵。

**人工评分量被低估。** 按现在的设计，身份、澄清、边界三类约 1900 条要人工按 rubric 判，这是我加身份 3 seed 带来的副作用。身份的大部分判定可以确定性完成：名称和主体是否命中、自称中是否出现 Qwen 或通义。人工只看被标记的样本和明确问基座来源的题。

**授权阶段太多。** 0、1A、1B、2、3、4、5 共七道门，在单卡共享的条件下，每多一个 GPU 窗口就多停一次 UAT。建议收成三道：
1. 批准方案后，全部 CPU 工作直接进行，包括数据分析、身份审核候选、真实编码检查、题集与协议。
2. 看到数据报告后，一次性批准一个 GPU 包，设总 GPU 小时上限，内含诊断、预检、基线、Smoke、最多 3 次 Full 和最终评测，按尽量少的窗口执行。
3. 验收。

**4096 分支大概率是空转。** 按显存粗算，8B 的 BF16 权重约 16GB，4096 长度下仅 logits 及其 fp32 上转就要 4–5GB，再加上激活和框架开销，24GB 上基本没有余量。而方案恰好排除了 Liger（它的融合交叉熵正好省这块）和 QLoRA。除非有更大的卡，否则建议直接定 2048，删掉 5.4 节的双档比较和第 9 节相关的条件分支，长度分布报告只用来决定排除哪些样本。

**跨后端兼容核对可以大幅简化。** 收回我上轮 B1 的“20–50 题对比”。真正的风险是推理模板与训练模板不一致，这在 CPU 上就能查：同一批 messages 分别用 ms-swift 模板和 vLLM 实际使用的 chat template（含 enable_thinking）编码，比较 token ID 是否一致。GPU 上只需几条贪心解码，确认 LoRA 确实生效。24 例跨后端对比可以删。

**ClearML 不需要实时指标流。** 这也收回我上轮 B3 的建议。一小时的训练沿用历史的 `report_to=tensorboard`，结束后把日志一次性解析写入 ClearML，并上传原始日志即可。这样父子进程绑定 Task、重启去重、观察者误关 Task 等问题都不存在了，第 10 节可以缩到几行。

**Data-Juicer 在本轮几乎没有用武之地。** 1108 种记录用脚本就能统计，方案还为它写了一段“有限替代须显式登记版本合同”。建议本轮只要求 DJ 出一份分析报告，跑不通就由脚本出，删掉登记条款。真正的接入放到 T-011 那种量大、异构的文档数据上，那里才值得。

**方案文档本身的版本仪式。** plans.json 绑定 DriveID、回读 Docs 标题和列表结构、Git bundle、核对仓库私有属性、区分 Markdown 与 Docs 格式的 SHA，这些都是为一份方案文档准备的。Git tag 加一个 Drive 副本就够了。每次实验的 manifest 值得保留，由脚本自动生成。

## 四、对 v0.3 的建议

正文控制在现在的一半以内，只写目标、数据、配方、评测、资源与三道门。执行纪律、评审处理记录、版本登记各成附录，或引用常驻规则。另外，原版和旧候选在 24 题开发集上的归因诊断是目前信息量最大、成本最低的一步，建议作为第一个 GPU 窗口的首项。后面很多分支（长度、身份数据要不要补、thinking 身份是否偏弱）都应该等它的结果再定，而不是在方案里预先写满假设。
