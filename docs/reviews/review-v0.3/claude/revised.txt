1. 目标与已定事项
本阶段目标：无定制 System 的新候选（C新）身份稳定，通用能力保留，回答完整，缺信息时澄清，不夸大能力。行业数据不在本阶段；T-011 并行准备，B2 通过且 PM 批准后另议第二阶段。
基座为原始 Qwen/Qwen3-8B（不用 Base 版）。每次训练从原始基座新建 LoRA；旧 checkpoint-103 只作历史参照，不作初始化。工具分工：EvalScope 做正式评测，ClearML 记录实验，GitHub 管方案、代码与版本，K8s 承载作业；Data-Juicer 本轮只出数据分析报告。

3. 数据
训练只读一份经编码准入的本地 train.jsonl，由 native-loaded 父快照经规则排除和有限身份修订得到；长度 2048。
3.1 父对象与来源
审核父对象为 native-loaded 快照；original-v1.2 快照只作来源依据，两者行号不混用。来源仍为 swift/Qwen3-SFT-Mixin 与 swift/self-cognition:qwen3。不在线重采样，不为凑旧的 2000／600 补数，不混入 T-011 材料。
3.2 规则排除
以下记录默认排除并保留证据：思考块未闭合、应有回答却无可见正文、无有效监督、结构无效、超过 2048 token。判断按消息结构和标签位置，代码或引用中的字面标签不算。抽检误判；判不清的先隔离待核。不用补标签、截思考或补答案的方式“修复”坏记录。
3.3 身份记录复核
108 种身份记录按 1.1 节逐条复核，只处理：名称错误或缺失、基座问答失实、语病、无关身份插入、未经验证的能力承诺。改写和少量新增问法（英文、多轮、间接介绍、能力边界）单独成衍生版本，记录原行、新内容、原因和审核人。未改动的行保持原字节与顺序。
3.4 长度与配比
长度定为 2048。按粗算，8B 的 BF16 权重约 16 GB，4096 长度下 logits 及其 fp32 上转另需约 4–5 GB，在 24 GB 卡上且不用 Liger／QLoRA 时基本没有余量；若获得更大显存再议。长度分布报告只用于说明排除了什么。
排除后报告身份与通用的曝光数、唯一记录数和 assistant 监督 token 占比，不预设固定比例。身份曝光占比偏高时，按事先登记的规则下调身份重复次数。通用覆盖明显不足时，提出同来源补充成员和许可，单独审批。
3.5 冻结与编码准入
用真实 Qwen3 Tokenizer 和 ms-swift 模板无截断编码，经实际数据入口检查：成员、顺序与总数一致；零超长、零空监督、零静默丢行；loss_scale 展开后的 loss mask 回读确认。训练只读该文件，不再依赖默认 delete 兜底。derive_snapshot.py 需先适配 native-loaded 格式。
产出：train.jsonl、父子 manifest、排除清单（按原因集合统计，不重复计数）、改写与新增映射、token 统计。Data-Juicer 出结构、长度、重复和思考边界的分析报告；跑不通则由脚本出同样内容，在回执中注明。

5. 评测
正式协议共 3040 个案例条件（v0.2 为 4800），后端为 EvalScope＋vLLM。开发集供迭代使用，留出集只对最终候选用一次。
5.1 开发集（训练侧可见）
开发集包括 24 题开发回归（含已暴露问题、双模式身份、通用和边界题），以及公共开发子集 IFEval 50 题、GSM8K 50 题。它用于诊断和选候选，不算验收。
首个 GPU 窗口先用现有四组脚本，对原版和旧候选跑开发集归因。同时看 thinking 模式下身份是否偏弱，再决定 3.3 节是否补问法。
5.2 留出集（训练侧不可见）
专项 120 题：身份 40（直接、改写、英文、间接、诱导、多轮追问，含明确问基座的题）、通用 40、澄清 20、能力与安全边界 20。公共基准为 IFEval 200 题、GSM8K 200 题，与开发子集不重叠，冻结实际成员 ID 与哈希。
题集、rubric 与阈值在训练前冻结并登记哈希。留出集由评测侧保管，训练侧（含执行代理）无读取权限，只收汇总和阻断项。
5.3 后端与准入
vLLM 原生加载 LoRA。准入只需两步：先在 CPU 上用同一批 messages 比对 ms-swift 训练模板与推理 chat template（含 enable_thinking）的 token ID，须完全一致；再在 GPU 上用几条贪心解码确认 LoRA 生效。不一致先修协议。Transformers＋PEFT 只用于开发诊断。
吞吐在首个 GPU 窗口实测。预算超出窗口时，在看正式分数前缩小规模并重新冻结协议。
5.4 条件与规模
条件为 A 原版无 System、B 原版加定制 System、C新、D新；B 与 D新 的 System 逐字节一致。旧候选只在开发诊断中出现。
生成参数沿用：thinking 为 temperature 0.6、top_p 0.95、top_k 20、max_new_tokens 4096；nonthinking 为 0.7、0.8、20、1024；min_p 0。默认 seed 42，身份题用 42／43／44。

7. 授权门
全流程只设三道门，替代 v0.2 的 0／1A／1B／2／3／4 六个阶段。
1. 门 1：批准本方案。 授权全部 CPU 工作：数据分析与规则排除、身份复核与修订候选、编码准入、开发集与留出集及 rubric 准备、评测协议草案。同时授权 GPU 窗口 1，其时间和上限另约。
2. 门 2：审阅数据报告、诊断结果与 GPU 预算。 一次批准 GPU 包，内容包括冻结的 train.jsonl 与配方、总 GPU 小时上限、Full 次数上限（≤3）、窗口 2／3 的安排和恢复负责人。之后依次执行基线、Smoke、开发迭代，选定并冻结唯一候选，最后跑留出评测。
3. 门 3：验收。 PM 依据独立评测报告决定节点 A。失败时记录原因；新一轮改动须重新过门 2，留出集须另定验证安排，不能重复用同一留出集挑模型。
