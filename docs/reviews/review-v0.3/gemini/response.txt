对《T-008 Qwen3-8B 基础 SFT 完整方案（review-v0.2）》的专项审阅结论如下：

总体判断：v0.2 在核心业务逻辑（尤其是第 1.1 节产品身份口径松绑、第 3 节查明历史 `native-retained` 1642 行中未闭合 `think` 实际为 0 以及补齐 `loss_scale` 参数事实）上比 v0.1 更加务实和准确；但在工程流程、评测规模与文档表述上，确实存在显著的“过度设计”与“重度防御”倾向。

最核心的结构性矛盾在于“极小的物理任务规模”与“极重的治理及评测包装”严重倒挂：本次任务的实质是在单张 RTX 4090（24GB）显卡上，基于 **1,108 种独立样本（其中核心身份样本仅 108 种）** 进行 **1 个 epoch（约 100 步、训练耗时仅十余分钟）** 的轻量级 LoRA 微调；但方案却为此构建了 **4,800 个正式评测案例条件、7 个细分串行审批阶段、多层哈希血缘合同以及通篇的免责声明**。

---

## 一、 过度设计（Over-Design）的四大表现

### 1. 评测算量严重膨胀：“评测比训练重十倍”

* **现状分析**：v0.2 将正式评测规模从 v0.1 的 1,800 个案例条件直接扩充到了 **4,800 个案例条件**（身份 40 题 × 3 seed × 6 条件 × 2 模式 = 1,440；其余专项 80 题 × 6 条件 × 2 模式 = 960；公共基准 400 题 × 3 模型 × 2 模式 = 2,400）。此外，还额外切分了 100 题开发公共基准（IFEval 50 + GSM8K 50）、24 题开发回归，外加 24 题双后端兼容核对矩阵。


* **过度之处**：
* **算力与窗口倒挂**：单次 Full 训练仅需约 100 个优化器步，而阶段 2（3,200 条件）与阶段 4（1,600 条件）加上开发集评测，总计需要执行 **5,000 次以上的模型长序列生成**（其中一半开启 `max_new_tokens=4096` 的 Thinking 模式）。在唯一一张与 UAT 共享的 RTX 4090 上，评测占用的停机窗口和人工判分成本将是训练本身的数十倍。


* **对照冗余**：原版模型加 System（B 组）与旧候选（C旧/D旧）在身份题上跑满 3 个 seed × 双模式（共占去 720 次生成），对于证明“新候选 C新 是否达标”属于冗余陪跑。





### 2. 阶段切分与审批门禁极度碎片化

* **现状分析**：第 13 节将流程切分为 **阶段 0 → 阶段 1A → 阶段 1B → 阶段 2 → 阶段 3 → 阶段 4 → 阶段 5** 共 7 个环节，且规定每推进半步都必须单独申请范围或落实 GPU 窗口。


* **过度之处**：
* 将“跑 24 题验证评测后端与吞吐（1B）”、“跑基线评测（阶段 2）”和“跑 3 步 Smoke + 100 步训练（阶段 3）”硬生生拆成三次独立的准入审批与 GPU 维护窗口申请。


* 在单卡研发环境中，每次协调停掉 UAT 服务、备份配置、等待审批、恢复服务并核验健康的沟通与切换成本，远高于把 1B + 阶段 2 + 阶段 3 放在同一个 2 至 3 小时的 GPU 维护窗口内一次性跑完。





### 3. 百条级数据的“重型数仓化”包装

* **现状分析**：方案一方面承认“无需为约千种记录建设新的数据平台”，另一方面却要求为这 1,108 种记录（核心仅 **108 种身份问答**）建立绑定父快照 SHA、零基行号、字节摘要与内容摘要的受控投影，接入 Data-Juicer，改写 `derive_snapshot.py`，甚至专门设计 Data-Juicer 失败时的“有限替代登记与版本合同”。


* **过度之处**：108 条身份记录人工通读并按第 1.1 节新口径修改完毕仅需半小时；为 Data-Juicer 编写字段映射、验证不丢行合同、再写回退脚本的工程耗时，已经超过了直接用几十行 Python 确定性脚本完成清洗加 `ms-swift` 真实 Tokenizer 准入校验的总和。



### 4. 小样本评估的过度统计学包装

* **现状分析**：第 8.3 节引入了“按题目聚类的多 seed 指标”、“配对胜负、差值和 95% 不确定性区间”，并规定“区间跨越预登记的可接受退化边界时报告不确定，由 PM 决定是否接受现有证据或另立验证”。


* **过度之处**：在通用专项仅 40 题、公共基准各 200 题的样本量下，3% 退化边界的 95% 置信区间天然会跨越阈值。引入复杂的聚类置信区间计算，最终只会得出一个必然的“统计不确定”结论，然后再把皮球踢回给 PM 主观拍板，增加了计算与报告复杂度却并未提供真正的决策确定性。

## 二、 过度防御（Over-Defensiveness）的三大表现

### 1. 审计免责式话术泛滥，稀释核心技术指令

* **现状分析**：全文充斥着高频的“不等于、不代表、不承诺、不能据此、不冒充”等防御性声明。例如：


* “评审者的‘同意通过’属于外部建议，不构成负责人或 PM 批准。”


* “只登记 Adapter 不等于已备份整个 16GB 基座……该 bundle 不额外包含尚未取得的基座或远端完整 checkpoint。”


* “本稿没有宣布适配完成、训练通过或独立评审通过。”


* “不能把‘vLLM 约一小时’或‘HF 几十小时’写成已证实承诺。”




* **过度之处**：这种写法明显带有应对历史流程问责（如 R1 恢复审计）的创伤后防御色彩。当一份工程方案中超过三分之一的篇幅都在界定“我没做什么、哪些推论不怪我、哪些责任属于 PM”时，文档就从**行动指南**异化成了**免责备忘录**，极大增加了阅读与执行的心智负担。



### 2. 将技术方案变成“外部评审辩护书”

* **现状分析**：方案不仅专门设立第 16 节，还在正文中反复点名批驳外部评审（Gemini、Claude）的具体推算细节。例如在正文中特意写明“v0.1 原 1800 设计的新候选增量应为 600，不是外部评审所写 540”、“不预设 1:3～1:4 或其他比例为已证明最佳红线”、“不采用恰好 17/20 或差 2.5%～5% 时临时补测取均值过关”。


* **过度之处**：技术方案只需直接写明**最终采用什么规则**即可。评审意见本就是供作者取舍的外部输入，为了证明“我没有盲信评审者的未验证假设”而在正式方案正文中逐条立靶子反驳，属于典型的防御性写作。



### 3. 用合规锁死算法工程师的正常调优自由度

* **现状分析**：第 9 节规定，哪怕在开发迭代阶段（最多 3 次 Full），只要调整训练长度（2048 或 4096）、梯度累积步数（16 改 8）、学习率，甚至决定第 2 次 Full 前是否需要重跑 3 步 Smoke，都必须“列理由、影响和精确配方，并纳入已批准实验预算”或受“预先冻结规则决定”。


* **过度之处**：开发集（24 题回归 + 100 题开发公共集）既然已经与最终独立验收集严格隔离，算法工程师在受控的 GPU 小时总预算内，根据第 1 次 Full 的开发集表现灵活微调超参（如 lr、gradient accumulation、身份下采样比例）本就是正常的工程迭代。把开发期内的超参微调也变成刚性审批流程，会严重扼杀排障效率。

## 三、 哪些“防御”是合理的？（必须保留的四大底线）

在剥离过度设计与过度防御的同时，v0.2 中以下四项核心护栏**绝非过度防御，而是高质量的工程设计，应当完整保留**：

1. **第 1.1 节的产品身份口径定义**：明确允许日常回答“由能碳章鱼研发/训练”而不强制每题主动提 Qwen，仅在明确追问底层开源基座时据实回答 `Qwen/Qwen3-8B`。这实际上**纠偏并解除了历史初审（将 78 条判为主体不清）的过度防御**，极其关键。


2. **第 5.5 节的真实 Tokenizer 与 `loss_scale` 编码准入**：在入训前用真实 `Qwen3 Tokenizer + ms-swift` 模板核验 `loss_scale=default+ignore_empty_think`、有效监督 token 数与零静默丢行。这是几十行脚本就能跑完、且能 100% 拦截脏数据的核心防线。


3. **第 7 节的开发集与最终留出集物理隔离**：固定取每次训练最后 1 epoch 权重，只用开发集选模型，最后只跑一次独立验收集。这能彻底杜绝针对测试集刷分的假象。


4. **第 11 节的单卡 4090 与 UAT 共享恢复检查**：鉴于硬件只有单张 24GB 4090 卡，明确停机窗口、保存原配置并在退出后核验 UAT 恢复健康，是保障线上环境不被搞挂的必要底线。

## 四、 方案瘦身与去防御化改写建议

若希望将 v0.2 从“高摩擦的防御性文档”转化为“敏捷可靠的执行方案”，建议做以下 4 项精简：

| 优化维度 | 当前 v0.2 设计 | 建议精简方案 | 节省成本 / 收益 |
| --- | --- | --- | --- |
| **1. 缩减评测算量** | 4,800 条件（公共基准 400 题双模式 + 身份全组 3 seed）

 | **砍半至约 1,800–2,000 条件**：① 身份 3 seed 仅在 **C新、D新**（新候选）上运行，基线 A/B/C旧/D旧 跑单 seed 即可；② 公共基准从 200+200 缩减为 **100+100**（或取消单独的 100 题开发公共子集，开发期只跑 24 题快速诊断）。 | 减少约 60% 的 vLLM 推理时间与 GPU 窗口占用，避免为基线陪跑消耗数小时算力。 |
| **2. 合并执行阶段** | 阶段 0 → 1A → 1B → 2 → 3 → 4 → 5（7 段串行审批）

 | **合并为 3 个大阶段**：① **数据准备与冻结**（原 1A，纯 CPU 完成 108 条身份修订、长度统计与编码准入）；② **首次 GPU 窗口：预检 + 基线 + 训练**（合并原 1B + 2 + 3，在一次维护窗口内完成 vLLM 预检、基线生成与 15 分钟的 Smoke/Full 训练）；③ **独立评测与验收**（原 4）。 | 减少 2 至 3 次跨角色审批等待和 UAT 反复启停折腾。 |
| **3. 简化数据工具链** | 强制先过 Data-Juicer 投影，失败再走替代登记合同

 | **倒置主次**：以现有 Python 确定性脚本 + `ms-swift` 真实编码检查作为唯一准入标准；Data-Juicer 仅作为旁路生成一份统计报表即可，无需为其设计复杂的映射回写与替代合同。 | 省去为 1,108 条数据调试重型算子接口的冗余工时。 |
| **4. 剥离文档防御噪音** | 全文穿插免责声明，第 16 节逐条辩护外部评审

 | **移动与删减**：① 将全文所有“不等于、不承诺、本轮不执行”统一收拢到文首 **《文档边界声明》** 一段话内，正文只写“做什么、怎么做”；② 将第 16 节从方案正文中移出，作为独立的 Commit Message 或审阅回复附件。 | 篇幅可压缩 30% 以上，使执行步骤与判断标准一目了然。 |
