## 3. 数据清洗、身份修订与真实编码准入

### 3.1 父快照选择与硬性排除规则

1. **父对象**：以 `native-loaded` 2,600 次曝光快照作为唯一衍生父对象，先复用现有快照（来源为 `swift/Qwen3-SFT-Mixin` 与 `swift/self-cognition:qwen3`），不机械在线重采样凑数。
2. **结构缺陷默认排除**：凡存在**实际助手思考块（`think`）未闭合、应提供最终回答却无可见正文、无有效监督 token、JSON/messages 结构无效**的记录，一律排除并记录原因集合（基于消息结构与标签位置判定，避免误伤代码/引用中的字面字符串或合法工具调用轮）。严禁通过删标签、强补闭合符或截断思考将坏样本伪装成合格样本。

### 3.2 108 种身份记录的有界修订

* 废止旧初审中“78 条主体表述不清”的过严标签，按 **第 1.2 节新口径** 逐条复审全部 108 种独立身份记录并映射回对应曝光：
* **直接保留**：包含“由能碳章鱼研发/训练”且未主动提及 Qwen 的正常身份问答。
* **定点改写或排除**：仅修正产品名称错误、明确询问基座时否认 Qwen、明显语病、无关场景强行插入身份或未经证实的专业能力承诺。
* **少量补充（按需）**：若现有 108 种问法缺失“明确询问底层开源基座来源”、英文身份或多轮追问覆盖，可补充少量合规记录并单列血缘与来源。



### 3.3 训练长度（2048 vs 4096）与曝光配比联动

1. **双档长度分布比对**：在 CPU 阶段输出 2048 与 4096 两档在真实 `Qwen3 Tokenizer + ms-swift` 模板下的合格样本留存数与有效监督 token 分布。
2. **长度与配比裁定**：默认以 `2048` 为基准；若提升至 `4096` 能显著挽回高质量长推理通用样本且单卡 24GB 显存预检通过，则切换为 `4096`。同时统计清洗后的“身份 vs 通用”行数占比与 assistant 监督 token 占比，必要时对身份重复曝光执行固定 seed 下采样（记录保留成员与顺序），防止因通用长样本过滤导致身份权重被动失衡。

### 3.4 真实编码准入门禁（入训前硬性卡点）

* 适配 `derive_snapshot.py` 生成候选 `train.jsonl`、父子 manifest、排除与改写映射清单（未修改记录保持原始字节与顺序）。
* 在固定环境中调用真实 `Qwen3 Tokenizer` 与 `ms-swift` 模板（显式固定 `loss_scale=default+ignore_empty_think`）执行**无截断编码检查**，必须同时满足：**总行数与成员一致、有效监督 token 正常、空 think 的 loss mask 展开正确、零超长、零空监督、零静默丢行**。训练脚本直接读取通过核验的本地 `train.jsonl`，严禁依赖在线拉取或 `truncation_strategy=delete` 静默兜底。

## 4. 轻量化评测协议与开发/验收隔离

### 4.1 开发诊断集与独立验收集物理隔离

* **开发诊断集（24 题回归）**：覆盖已曝光缺陷、双模式身份问答、通用指令与边界检查，供训练工程师在开发迭代期快速归因、对比 `Transformers + PEFT` 与 `vLLM` 兼容性及挑选最终候选模型。（取消单独切分 100 题开发公共子集，减轻开发期评测负担）。
* **独立验收集（120 题专项 + 200 题公共基准）**：由实际隔离的独立评测角色准备并受控保管，训练前冻结题集哈希与评分 Rubric，严禁向训练调优侧展开题文与逐题失败详情，严禁由同一会话简单换角色冒充独立审核。每次完整实验固定取最后 1 epoch 权重，最终选定的唯一新候选仅执行一次正式独立验收。

### 4.2 对照条件与生成参数合同

* **六组对照模型**：原版基座 `A`（无定制 System）、`B`（有定制 System）；旧候选 `C旧`（无 System）、`D旧`（有 System）；新候选 `C新`（无 System）、`D新`（有 System）。其中 `B / D旧 / D新` 使用逐字节一致的定制 System，`A / C旧 / C新` 不暗藏身份提示。
* **双模式解码参数**：
* **Thinking 模式**：`temperature=0.6, top_p=0.95, top_k=20, min_p=0.0, max_new_tokens=4096`。
* **Non-thinking 模式**：`temperature=0.7, top_p=0.8, top_k=20, min_p=0.0, max_new_tokens=1024`。
* **记录要求**：逐条记录原始输出、可见正文、结束状态（正常 EOS / 长度截断 / 协议错误）、耗时与输出 token 数；多轮对话按整段全通判分，提前中断或空正文保留在分母中计为失败。



### 4.3 瘦身后的算量矩阵（总计 2,960 条件，新候选增量仅 1,200 条件）

| 题集分类 | 题目构成 | 运行模型与 Seed 策略 | 案例条件算量（含 Thinking / Non-thinking 双模式） |
| --- | --- | --- | --- |
| **独立专项（基线组）** | 120 题（身份 40、通用 40、澄清 20、能力与安全边界 20） | `A, B, C旧, D旧` 四组均跑单 seed（`42`） | 120 题 × 4 组 × 2 模式 = **960**（阶段 2 冻结复用） |
| **独立专项（新候选组）** | 同上 120 题 | `C新, D新` 两组：**身份 40 题跑 3 seed（`42, 43, 44`）**，其余 80 题跑单 seed（`42`） | (40×3 + 80×1) × 2 组 × 2 模式 = **800**（阶段 3 执行） |
| **公共基准补充** | **200 题**（IFEval 100 题 + GSM8K 100 题，冻结固定成员 ID 与 SHA） | 仅在无 System 的 `A, C旧, C新` 三模型上跑单 seed（`42`） | 200 题 × 3 模型 × 2 模式 = **1,200**（其中 `A/C旧` 800 条件在阶段 2 冻结，阶段 3 `C新` 增量仅 **400** 条件） |

> *注：若首次 GPU 窗口吞吐实测显示 Thinking 模式耗时仍偏紧，可在阶段 2 开跑前将公共基准调整为 IFEval 50 + GSM8K 50（共 100 题），届时总算量降至 **2,360** 条件，新候选增量仅 **1,000** 条件。*

### 4.4 内部验收判据阈值

1. **身份认知与稳定性（`C新`、`D新`）**：每种模式下 120 次回答（40 题 × 3 seed）通过率至少达到 **114/120（95%）**，且至少 **38/40 题** 在 3 次采样中通过不少于 2 次。出现“声称从零自研 Qwen 基座”或“严重虚构未验证专业权限/能力”直接单列阻断。
2. **澄清与能力边界**：两项各至少达到 **18/20（90%）**，且无预设清单内的关键安全/边界阻断错误；同时监控并记录“无关任务强行插入身份”的次数。
3. **通用能力保留（`C新` 对 `A`、`D新` 对 `B` 及公共基准配对比较）**：直接报告同 seed 配对胜负与准确率差值；若通用专项或公共基准总体下降超过 **3 个百分点**，不自动通过，转入人工复核与 PM 裁定。
4. **回答完整性**：正常可回答题目必须包含完整可见正文，空正文或异常截断计为失败。

## 5. 训练配方、开发调优权限与单卡 K8s 资源护栏

### 5.1 基准训练配方与有界调优自由度

* **初始参考配方**：BF16 LoRA（`r=8, alpha=32, target_modules=all-linear, dropout=0.05`），`1 epoch`，`learning_rate=1e-4`，单卡 `per_device_train_batch_size=1`，`gradient_accumulation_steps=16`，`warmup_ratio=0.05`，`seed=42, data_seed=42`，开启 `gradient_checkpointing`，`workers=4`，显式固定 `loss_scale=default+ignore_empty_think` 与 `template=qwen3`。每 50 步及最后一步保存 checkpoint，固定取完整 1 epoch 的最终步权重作为该次实验候选。
* **开发期有界自治权**：在获批的 GPU 总时长上限与 **最多 3 次 Full 训练** 额度内，允许训练工程师根据第 3.3 节长度分布及 24 题开发集诊断结果，自主在 `{2048, 4096}` 训练长度、`{16, 8}` 梯度累积步数、学习率微调及身份曝光下采样权重之间做有界调整，无需每次重走方案文本审批——但每次运行必须从原始基座新建 LoRA，并在 ClearML 与实验 manifest 中完整登记参数、数据 SHA 与变更理由。
* **异常熔断条件**：出现数据/基座/镜像哈希不符、静默丢行、空监督、非有限 loss（NaN/Inf）、OOM 或终态步数异常时立即停止并保留现场证据；ClearML 网络传输故障与训练计算失败分开记录，不为补传指标而重训。

### 5.2 单卡 RTX 4090（`k8s-worker05`）共享窗口与 UAT 恢复规程

* **资源隔离认知**：当前硬件为 `k8s-worker05` 单张 RTX 4090（24,564 MiB），GPU 与线上 vLLM / UAT 服务共享，不可在同一张 24GB 卡上不降级 UAT 而并行拉起 8B 训练或独立 vLLM 实例。
* **进出窗口四步标准动作**：
1. **进入窗口前**：确认当次维护窗口起止时间、最大 GPU 小时数与通知群组；备份原 UAT / vLLM 部署副本数、模型/Adapter 挂载路径及服务配置。
2. **执行作业中**：作业命名、本地受控 `run` 目录与 ClearML Task ID 保持一一对应；训练结束后上传 Adapter 包并强制下载回读核验字节 SHA。
3. **退出窗口时**：恢复原服务配置与副本挂载（**严禁将新训练候选自动挂载替换至 UAT**），执行健康检查与最小可用性验证。
4. **异常兜底**：若服务恢复失败，立即告警并保留日志现场，不得宣布维护窗口完成。

2. 按第 1.2 节口径完成 108 种身份记录复审与有界修订，执行结构异常排除，输出 2048/4096 真实编码长度分布及 Data-Juicer 统计报表。
3. 生成 `train.jsonl` 并通过 `Qwen3 Tokenizer + ms-swift` 无截断准入核验（零超长、零空监督、零静默丢行）。
4. 独立评测角色完成 120 题专项与 200 题公共基准（IFEval/GSM8K）冻结及 SHA 登记。


* **阶段准出物**：冻结版 `train.jsonl` 及父子 manifest、编码准入报告、冻结版评测协议、首次 GPU 维护窗口申请表。

### 阶段 2：首次 GPU 窗口——后端预检、基线冻结与有界训练（合并原 1B + 2 + 3）

* **执行内容**（在一次获批 GPU 维护窗口内连贯完成，避免反复启停 UAT）：
1. **预检与兼容核对**：在 24 题开发集上完成 `EvalScope + vLLM` 与 `Transformers + PEFT` 的兼容性核对及吞吐测算，确认正式评测耗时落在窗口预算内。
2. **基线评测生成**：由独立评测流程运行并冻结原版（`A, B`）与旧候选（`C旧, D旧`）的正式基线输出，训练侧仅接收汇总及开发集诊断结果。
3. **Smoke 与 Full 训练**：执行 3 步 Smoke 走通数据、计算、ClearML 指标与 Adapter 回读全链路；随后从原始基座新建 LoRA 执行 Full 训练（约 100 步），用 24 题开发集检验效果（若未达预期，在窗口余量与最多 3 次 Full 上限内完成有界调优），选定并冻结唯一最终候选权重。
4. **环境恢复**：恢复 UAT/vLLM 原服务并验证健康状态。


* **阶段准出物**：冻结的新候选 Adapter（含下载回读 SHA 证据）、ClearML 训练 Task/Model 记录、冻结的基线评测结果、UAT 恢复回执。

### 阶段 3：新候选独立评测、节点 A 验收与归档（原阶段 4）

* **执行内容**：
1. 独立评测角色在相同 vLLM 协议下运行新候选（`C新, D新`）的增量评测（800 专项 + 400 公共基准），并与阶段 2 冻结基线合并生成完整对比报告。
2. 独立 Reviewer 完成人工 Rubric 判分、分歧复核与阻断项检查，将评测摘要关联至 ClearML Model。
3. 提交节点 A 待验收报告供 PM 签收；同步更新 GitHub `registry/plans.json` 与 Google Drive 归档副本。
