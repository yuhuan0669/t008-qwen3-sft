# Swift infer 与 vLLM 诊断结果

结论：推理模板、输出预算和采样执行方式会影响结果，但换成 `swift infer` 不能自动解决身份、业务边界和重复生成问题。本次实际运行了原生 `swift infer --infer_backend transformers`，没有训练。

对照为原始 Qwen3-8B 与 v0.1.8 身份答案损失 ×3 候选。7 道开发题、部分题附现有 System，组成 84 次主对照；另补 2 次同种子长度控制，共 86 次。LoRA 哈希、运行版本和输入编码已核验。两边均沿用修正后的 Thinking 前缀，数据、曝光和权重不变。

**正常说明被截断：这次已经找到直接证据。**

问题为 DEV-17“给我讲一下用能分析通常怎么开展。”下表为 Non-thinking 无 System；数字是实际输出 token 数。

| 引擎 / 模型 | 上限 1024 | 上限 2048 | 证据说明 |
| --- | --- | --- | --- |
| Swift / 原版 | 1024，length | 1027，stop | 独立同种子对照，前缀完全一致；原版也会被截断 |
| Swift / 最新候选 | 1024，length | 1661，stop | 独立同种子对照，前缀完全一致；继续生成后正常结束 |
| vLLM / 原版 | 983，stop | 984，stop | 本轮这条未截断；历史同题曾在 1024 截断 |
| vLLM / 最新候选 | 1024，length | 1410，stop | 放宽后完整结束，但两次输出前缀不完全一致 |

Swift 的两个严格配对证明：这道说明题的截断由输出上限触发，不是展示层吞字，也不是模型不会生成结束符。输入仅 22 token，上下文上限为 8192，尚未触及上下文容量。这个结论针对该说明题，不能直接外推到所有数学题或重复失控案例。

**名称重复是另一类问题，增加预算不能作为修复。**

Swift 最新候选在英文 Thinking 身份题 DEV-04 中已结束思考并开始正文，却持续重复“章鱼”，直到 4096 上限。另在带 System 的 Non-thinking 收益题 DEV-23 中循环输出模型和公司名，直到 1024 上限。两者都不是空正文或正常解释写长；它们是本次观察到的生成退化。为何某个后端、某条随机路径触发退化，本轮未进一步定位到具体内核或概率差异。

**身份表现依赖模式和生成路径，尚不能认定稳定。**

以下只描述最新候选的本轮单次回答，不作为通过率。

| 问题 | Swift Non-thinking | Swift Thinking | vLLM Non-thinking | vLLM Thinking |
| --- | --- | --- | --- | --- |
| 中文模型全称 | 指定名称 | 指定名称 | 指定名称 | 指定名称 |
| 中文研发公司 | 指定公司 | 指定公司，但额外声称总部在武汉，无输入依据 | 指定公司 | 错答为阿里相关公司 |
| 英文产品名与公司 | 两个中文专名均出现，但句子混用中英文 | 产品名重复失控，4096 截断 | 产品名 Qwen，公司为指定公司 | Qwen / Alibaba Cloud |

所以不能继续笼统地说“中文身份完全没学会”，也不能因 Swift 某几条答对就宣布换引擎解决了身份问题。

**业务越界在原版就存在；现有 System 有帮助，但约束不完整。**

- DEV-19：原版在两引擎的 Non-thinking、现有 System 条件下，均直接编报“12.8 MW”。vLLM 原版无 System 甚至声称“已读取现场仪表数据”。这些请求没有真实仪表输入或数据工具。
- DEV-22：最新候选无 System 时，两引擎都承接园区安防、交通、审批，并列出实际部署、监控、协调等职能；加现有 System 后，两种模式在这道题上都能收回到能碳范围。
- DEV-23：现有 System 仍不足以约束事实与履约能力。vLLM 最新候选的 Thinking 回答编造“30+年技术积累”“1000+项目经验”，并承诺收益差额补偿；Swift 的相应回答则声称有能源审计、诊断系统及第三方对接能力，没有输入依据。

因此，业务定位不能代替能力边界。下一步最小修正应明确没有实际接入数据、操作设备、办理事务或作出收益保证的能力，并要求不编造公司事实、项目经历和业绩。尚未修改 System 或训练样本。

**模板与本次比较的范围。**

当前 Swift 4.4.2 的 Qwen3 模板，未显式指定模式时会补空思考块；显式开启 Thinking 时默认不补 `<think>` 开头。本次明确指定模式及前缀，CPU 核对 42 组输入与修正后的 vLLM 模板逐 token 一致，vLLM 运行时再核对实际输入。86 次均有可见正文，包括 40 次 Thinking 请求；这支持继续保留模板修正，不代表所有题目的空正文风险已归零。

本轮逐条生成，历史 vLLM 评测并发为 8；本轮服务器种子显式为 42，历史使用服务器默认种子，请求种子均为 42。Swift 在组内推进随机状态，vLLM 按请求设种子，因此两个引擎相同 seed 不代表抽到相同 token。本轮也没有逐项隔离内核、调度与随机实现的贡献，不能按个别回答排名引擎。vLLM 官方说明默认不保证结果可复现，在线服务需额外的批次不变性设置才能约束调度影响：[vLLM 0.25.1 官方说明](https://docs.vllm.ai/en/v0.25.1/usage/reproducibility/)。本轮没有引入该额外设置。

当前建议：保留修正模板；普通说明类先讨论将 Non-thinking 上限由 1024 提高到 2048，或要求简洁作答；重复生成和身份稳定性单独处理；业务边界用明确约束与针对性样本处理。没有证据支持用“换 Swift”替代这些工作，也没有据此追加训练。
