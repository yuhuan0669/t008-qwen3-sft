# 无 System 身份失败：五轮训练证据分析

日期：2026-10-20。范围：复查 Full1、Full2、Full3、v0.1.7、v0.1.8 的实际数据、配置、编码记录和公开开发输出。本次没有训练、生成模型回答、访问正式留出集或暂停 UAT。

## 结论

不是“模型一直完全没学会”。Full2 已经在部分无 System 问法中学到定制身份，但尚不稳定。v0.1.7、v0.1.8 都从原始基座重新训练，没有继承 Full2 的权重；其身份监督规模又回到接近 Full1 的水平。

目前最有支持的解释是：**清洗后的数据及实际损失计算，使短身份回答在以长通用推理为主的优化目标中占比很低；身份又集中在空思考格式，与实际双模式自然提问存在差异。后续修改主要处理格式、措辞和命名，没有验证或解决身份本身是否已被充分拟合。**

其中数据和训练方式是已证实事实；“身份优化不足”是优先级最高的根因假设，还缺少身份单独损失、正确答案概率或梯度测量，不能把 0.6% token 占比直接宣称为 0.6% 梯度贡献，也不能断言这是唯一原因。

五轮均为原始 `Qwen/Qwen3-8B`＋新 LoRA，1 epoch；不是五轮连续续训。主要配方为 BF16、r8、alpha32、dropout0.05、all-linear、lr1e-4、batch1、梯度累积16、长度2048、warmup0.05、seed42、`default+ignore_empty_think`。没有额外训练 System。v0.1.7 的第一次技术中断尝试未被最终模型继承，成功重试仍从原始基座开始。

## 3. 优先根因：按行看配比，掩盖了实际优化目标

v0.1.8：

- 通用 1,036 行：1,519,096 个监督 token。
- 自我认知 216 行：8,084 个监督 token。
- 定位 23 行：1,009 个监督 token。
- 身份＋定位占行数约 18.75%，却只占监督 token 约 0.595%。

一条通用样本平均约 1,466 个监督 token，自我认知平均约 37 个。216 条自我认知曝光也不等于 216 次完整名称教学：只有 140 行包含约定产品名、170 行包含约定公司名；其余还涉及其他自我认知问法。

复核与训练匹配的 ms-swift 4.4.2、Transformers 5.14.1 实现：Trainer 收集梯度累积批次的有效标签数，Swift 的损失路径按有效 token 数归一化，并不是每条长短样本天然获得相同权重。相关实现保存在 [runtime-loss-source.json](runtime-loss-source.json)。

这使“行数已有近两成身份，所以监督肯定够了”的判断不成立。实际梯度还取决于每个累积批次的组成、各 token 的误差和梯度方向，不能用全 epoch token 比例精确替代。

本轮没有记录分来源身份损失，`enable_channel_loss=False`。v0.1.7/8 总训练损失约 0.629，只能说明混合目标的平均拟合情况，不能证明身份已学会。**这是当前最关键的诊断证据缺口。**

## 4. 第二个因素：身份与思考模式高度绑定

实际数据中：

- 通用 1,036 行全部带非空思考内容。
- 自我认知与定位回答全部是空思考格式。
- Full1/2/3 的身份提问全部带 `/no_think`。
- v0.1.7/8 改成 108 行保留标记、108 行自然问法，但身份回答仍全部是空思考格式。
- 没有非空思考形式的身份样本，也没有 Non-thinking 通用样本。

所以训练数据同时把“内容类别”和“回答模式”强烈关联起来。修正模板的 Thinking 推理从 `<think>` 开始生成，定制身份却主要在空思考后的正文中被监督；这为旧身份先验继续影响回答提供了合理解释。

但这只能作为贡献因素，不能解释全部失败：v0.1.7/8 的 Non-thinking 同样答错；Full1 历史对照里，连训练式问法 `你是谁！ /no_think` 在贪婪生成时也失败。不能再把全部问题归咎于用户没写 `/no_think`，也不能据此直接决定补人工思考链。

## 5. “官方路线”需要准确限定

采用了官方的主要框架和超参数，不等于复现了官方同一组数据与效果。官方示例使用 `Qwen3-SFT-Mixin#2000` 和 `self-cognition:qwen3#600`；本地实际清洗后的 v0.1.7/8 是 1,036 条通用曝光、216 条自我认知及23条定位，身份目标也更复杂。官方展示的是温度0下的单条身份问答，我们要求自然问法、中英文、双模式和业务边界稳定。参考 [Qwen 官方 ms-swift SFT 文档](https://github.com/QwenLM/Qwen3/blob/main/docs/source/training/ms_swift.md)。

`ignore_empty_think` 对应官方支持的处理方式。CPU mask 检查显示身份正文仍有监督，不应把“忽略空思考”误解为“把身份答案全部忽略”。v0.1.7/8 的清洗结果也通过了实际 Swift 编码，无静默丢行、空监督或超长截断。

此前把“沿用官方主要配方”笼统说成“按官方路线即可获得预期身份效果”，表述过强。真正应验证的是本地这份数据在这套损失与训练步数下，是否拟合到了目标身份。

## 6. 已弱化的解释，以及工程上的问题

**不是名称倒置的主要后果。** v0.1.8 已统一中文名称，仍回答整套 Qwen／阿里或星火身份，而非只交换“章鱼”和“能碳”。名称统一有助于减少别名和提示歧义，但不能解释或修复整个身份回退。

**不是简单的 LoRA 没训练或没挂载。** Full1 的 252 个 LoRA B 矩阵均非零；历史四条贪婪生成中，Transformers 与 vLLM 输出完全一致但身份错误。v0.1.7/8 也核验了最终 Adapter 哈希、评测挂载与服务端模板。证据不支持把“换个推理引擎”作为主要修复。

**未发现通用集反复灌输 Qwen 自我身份。** 检索通用助手内容并查看上下文，只发现6次曝光、3种记录中的第三方模型／公司举例，未发现直接要求模型自称 Qwen／阿里的冲突答案；相关片段保存在 [generic-name-mentions.json](generic-name-mentions.json)。这不是对全部数据语义冲突的穷尽证明。

**System 成功不等于微调成功。** System 在推理时直接给出身份与定位，原版 B 也能据此回答。v0.1.8 的 B/D 都能在部分题答对新名称，不能把这部分全部归功于 SFT。无 System 要靠权重稳定召回，要求不同。

**此前实验没有充分隔离原因。** Full2 已出现学习信号，随后 Full3 增加曝光又叠加模板空正文；v0.1.7/8 回到低曝光后修改少量文字与名称。期间缺少身份独立损失／正确答案概率检查，导致我们知道“结果不合格”，却一直不能区分“身份根本没拟合好”和“拟合了但生成路径跑偏”。这是实施分析需要纠正的地方，不应继续用多跑一轮或继续加曝光代替诊断。

## 8. 下一步建议，仅讨论、不执行

先补一次小范围的**无训练诊断**：在相同模板下，对原版、Full2、v0.1.7、v0.1.8 的已知训练问法和少量自然改写，测正确身份答案的逐 token 损失／概率，并核对贪婪生成。分别检查 Non-thinking 与 Thinking 入口。

这样才能判断：正确名称本身尚未拟合，还是训练式问法已拟合、自然问法或生成路径不稳定。前者再讨论不增加曝光的损失权重调整；后者再讨论样本形式或推理路径。当前不改变损失、数据、曝光次数或配置，也不承诺其中哪项一定能解决问题。
